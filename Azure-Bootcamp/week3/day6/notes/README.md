# AI Log Analyser — Week 3 Day 6 Capstone

A FastAPI app that accepts a log file or raw log text and returns an
AI-generated root-cause summary, using a real Azure OpenAI deployment
(`gpt-5-mini`). Containerised, deployed to AKS via an Azure DevOps CI/CD
pipeline, with all secrets sourced from Azure Key Vault through the
Secrets Store CSI driver — no secrets in code, env files, or manifests.

## Status: complete and verified live

This capstone is fully built, deployed, and confirmed working end to end
against the real internet-facing deployment — not just locally.

Confirmed live, via direct `curl` against the AKS LoadBalancer's public
IP:
- `/healthz` → `200 {"status":"ok"}`
- `/readyz` → `200 {"status":"ready"}` (secrets present, pulled from Key
  Vault)
- `/analyse/text` → `200`, with a real, structured root-cause analysis
  generated by `gpt-5-mini` for a sample PostgreSQL connection-refused
  log

## Architecture

```
git push (Azure DevOps Repos)
        │
        ▼
Azure Pipelines (azure_pipeline.yml)
        │
        ├─ Build stage: docker buildx → multi-arch image → push to ACR
        │
        └─ Deploy stage (deployment job, needs explicit checkout: self):
                1. kubectl apply -f manifests/   (Deployment, Service,
                   SecretProviderClass — idempotent, safe to rerun)
                2. kubectl set image             (point at new image tag)
                3. kubectl rollout status        (wait for healthy rollout)
                        │
                        ▼
                AKS cluster (aks-bootcamp-week3)
                ├─ 2x ai-log-analyser pods
                │     ├─ env vars sourced from K8s Secret
                │     │  "azure-openai-secrets" (synced by CSI driver)
                │     ├─ readinessProbe: /readyz
                │     └─ livenessProbe:  /healthz
                ├─ Secrets Store CSI driver (AKS add-on)
                │     └─ authenticates via AKS's auto-created managed
                │        identity, reads from Key Vault
                └─ Service (LoadBalancer) → public IP → internet
                        │
                        ▼
        Azure Key Vault (kv-bootcamp-week3)
        ├─ azure-openai-endpoint
        ├─ azure-openai-api-key
        └─ azure-openai-deployment
                        │
                        ▼
        Azure OpenAI resource (vibha-mqyv8dko-eastus2)
        └─ gpt-5-mini deployment
```

## Running locally

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

export AZURE_OPENAI_ENDPOINT="https://<your-resource>.openai.azure.com/"
export AZURE_OPENAI_API_KEY="<your-key>"
export AZURE_OPENAI_DEPLOYMENT="gpt-5-mini"
export AZURE_OPENAI_API_VERSION="2025-04-01-preview"

uvicorn main:app --reload --port 8005
```

Without the env vars set, the app still runs — `/healthz` works,
`/readyz` and `/analyse/*` correctly report missing config (503) instead
of crashing.

In AKS, these same four names are populated automatically by the
Secrets Store CSI driver — the app code has no idea whether a value
came from a local `.env`, a plain Kubernetes Secret, or Key Vault.

## Real bugs hit during this build, and their fixes

These are documented here because they're exactly the kind of thing that
silently breaks again if the underlying cause is forgotten.

1. **`openai==1.51.0` + newer `httpx` → `TypeError: unexpected keyword
   argument 'proxies'`.** Only surfaces once real config is present
   (i.e. passes all testing until credentials exist, then breaks).
   Fixed by pinning `openai==1.58.1`.

2. **`gpt-5-mini` rejects `temperature` and `max_tokens` outright (400
   error).** GPT-5-family models are reasoning models; they use
   `max_completion_tokens` instead and don't accept `temperature` at
   all. Fixed in `analyser.py`.

3. **Empty response from `gpt-5-mini` even with no API error.**
   Reasoning models spend part of the token budget on hidden reasoning
   tokens before writing visible output. At `max_completion_tokens=800`,
   the budget was fully consumed by reasoning, leaving nothing for the
   actual answer. Fixed by raising the budget to `2000` and adding
   `finish_reason`/`reasoning_tokens` to the error message so this is
   diagnosable if it recurs.

4. **Dockerfile `COPY app/...` → `"/app": not found`.** The Dockerfile
   was adapted from a Week 2 project that had source files in an `app/`
   subfolder; this project's files sit flat in `day6/`. Fixed by
   removing the `app/` prefix from both `COPY` instructions.

5. **Deploy stage: `kubectl apply` → `the path "...manifests/" does not
   exist`.** Azure DevOps **deployment jobs** (`deployment:` blocks,
   unlike regular `job:` blocks) do not automatically check out the
   repo on their agent. Fixed by adding `checkout: self` as the first
   step under `deploy: steps:`.

6. **Kubernetes service connection creation failed with `401
   Unauthorized`** when using "Azure Subscription" authentication —
   Azure DevOps couldn't create the role binding it needed. Worked
   around by selecting "Use cluster admin credentials" instead, which
   skips that role-binding step entirely.

7. **Key Vault `setSecret` → `(Forbidden) ForbiddenByRbac`.** The vault
   was created with `enableRbacAuthorization: true`; being the creator
   does not automatically grant secret read/write. Fixed by explicitly
   assigning yourself the **Key Vault Secrets Officer** role, and
   separately assigning the AKS add-on's managed identity the **Key
   Vault Secrets User** role.

## Deliberate design decisions

- **No Ingress.** Service is `type: LoadBalancer`, exposing a public IP
  directly. Simpler for a bootcamp-scale single-app deployment; an
  Ingress would only be worth it with multiple services to route
  between.
- **No mocked/stubbed OpenAI responses, ever.** Every failure mode (no
  config, bad config, unreachable endpoint, empty model response) was
  designed to fail honestly with a clear error, not silently fake
  success.
- **`analyser.py` is isolated from `main.py`** specifically so that
  swapping models, SDKs, or providers later only touches one file.
- **Liveness probe stays on `/healthz`, not `/readyz`.** A liveness
  failure causes Kubernetes to kill and restart the pod — the right
  response to "the process is stuck," but the wrong response to "Key
  Vault is temporarily unreachable." Only the readiness probe moved to
  `/readyz`, so a config/secrets problem holds traffic back without
  triggering pointless restarts.

## Cost notes

Running this continuously costs roughly $0.05–0.06/hour in Azure
infrastructure (AKS node + Standard Load Balancer + public IP — the AKS
control plane itself is free on the Free tier). GPT-5-mini token costs
for testing at this scale are negligible (well under a cent per call).

down and rebuild.
